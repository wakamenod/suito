* Suito
** 全体の構成
リポジトリは3本立て。

| ディレクトリ | 中身 |
|--------------+------|
| =mobile/=    | 本体の Flutter アプリ (iOS / Android) |
| =web/=       | Google Play Store の「データ削除ポリシー対応」用の極小 Flutter web アプリ ([[https://web.suito.wakamenod.com][アカウント削除ページ]]) |
| =supabase/=  | Supabase CLI 管理下のマイグレーション・Edge Function・pgTAP テスト |

バックエンドは Supabase (Auth + Postgres + RLS + pg_cron + Edge Functions) に全面移行済み。
Flutter からは =supabase_flutter= で PostgREST / RPC を直接叩いており、間に API サーバーはない。

移行の背景・フェーズ分けは [[file:docs/SUPABASE_MIGRATION.md][docs/SUPABASE_MIGRATION.md]] を参照。

*** Supabase 側の構成
- スキーマ・RLS・関数・cron はすべて =supabase/migrations/= のマイグレーション
  (=0001_extensions= 〜 =0009_app_config_min_required_only=)
- テナント分離は RLS。全テーブルに =user_id = auth.uid()= のポリシーを張り、
  アプリ側の =WHERE uid = ?= を置き換えている
- テーブル権限は =0006_grants.sql= が明示的に付与する。=public= スキーマは既定で
  何も公開せず、=authenticated= にだけ必要な verb を渡す
  (=anon= が触れるのは =app_config= の SELECT のみ)。
  そのためプロジェクト設定の「Automatically expose new tables」は OFF でよい
- 定期取引エンジンは =enqueue_transaction_schedules()= と
  =create_transactions_from_queue()= (どちらも =SECURITY DEFINER=) を =pg_cron= で毎時実行。
  論理削除済みスケジュールが残した queue 行は、=create_transactions_from_queue()= が
  取引を作らずに消化する (=0007=。=DELETE ... USING= 側で弾くと queue 行が残るため
  =INSERT ... SELECT= 側でフィルタしている)
- 収入は固有の =title= を持たず表示名を =income_type= から借りるため、使用中の
  収入種別は削除できない (=0008= の =BEFORE DELETE= トリガーが =23503= で弾く)。
  論理削除済みの収入しか参照していない種別は削除できる。
  支出は自前の =title= を持つのでカテゴリー / 購入場所は =on delete set null= のまま
- チャートの集計は =column_chart_data()= / =pie_chart_data()= / =transaction_months()= の RPC。
  月軸のパディングと取引一覧のマージだけ Dart 側に置いている
- アカウント削除は Edge Function =delete-account=。呼び出し元の JWT を検証し、
  自分の =user.id= 以外は削除できない。各テーブルの =auth.users= への FK が
  =ON DELETE CASCADE= なので、Auth ユーザーを消せば全データが消える
- Free プランは7日間アクセスが無いと自動 Pause されるため、
  =.github/workflows/supabase-keep-alive.yml= が1日1回 REST API を叩いている

** シークレットスキャン (gitleaks)
コミット・CI の両方で [[https://github.com/gitleaks/gitleaks][gitleaks]] を使い、認証情報の混入を防いでいる。

- 設定は =.gitleaks.toml=。デフォルトルールに加え、Supabase ローカルスタックの
  デモ用キー (=iss: supabase-demo= の JWT) や =Podfile.lock= のチェックサムなどの
  誤検知を allowlist している
- CI は =.github/workflows/gitleaks.yml= が PR と main への push で全履歴を走査する
- ローカルでは pre-commit フックでステージ済みの差分を検査する。初回のみ以下を実行:

#+begin_src sh
brew install gitleaks
just install-hooks   # git config core.hooksPath .githooks
#+end_src

- 手動実行:
  - =just scan-secrets= … git 履歴全体 (CI と同じ検査)
  - =just scan-secrets-dir= … 作業ツリー全体 (git 管理外のファイルも含む)
  - =just scan-secrets-staged= … ステージ済みの差分のみ
- 誤検知は =.gitleaks.toml= に allowlist を足すか、該当行に =gitleaks:allow= を書く。
  フックを飛ばしたいときは =git commit --no-verify=

** 強制アップデートの非常ブレーキ
=version_check.dart= は =app_config.min_required_version= より古いビルドを、
閉じられないダイアログでブロックする。**リリースのたびに触るものではない。**

- 比較はセマンティック (=1.10.0 > 1.9.0= を正しく判定する)。既定値の =1.0.0= は
  これまで出したどのビルドより小さいので、**この行を一度も触らなければ誰もブロックされない**
- 判定は fail open。値が壊れていても (空文字列、=v1.0.3=、=1.0.3-beta=)、
  通信に失敗しても、ブロックしない。誤って通すコストより誤って閉じ込めるコストが桁違いに大きいため
- 取得は起動時と、フォアグラウンド復帰時のみ。さらに6時間のスロットルが掛かる

#+begin_src sh
$ just show-app-version              # 現在の値を確認
$ just require-app-version 1.0.3     # 1.0.3 未満をブロック (非常時のみ)
$ just release-app-version           # 1.0.0 に戻す (ブレーキを解除)
#+end_src

- =require-app-version= は **修正版がストアからダウンロードできるようになってから**
  実行すること。先に打つと、まだ落とせない更新を要求されたユーザーが操作不能になる
- =.env.suito.prod= (gitignore 済み) に以下が必要:

  #+begin_src sh
  SUPABASE_URL=https://<project-ref>.supabase.co
  SUPABASE_SERVICE_ROLE_KEY=<Dashboard > Project Settings > API の service_role キー>
  #+end_src

  このキーは RLS を無視できるので、コミットもログ出力もしないこと。
  =just scan-secrets-dir= は git 管理外も走査するのでこのファイルを検出する
  (=scan-secrets= / =scan-secrets-staged= は git 管理下だけなので影響しない)
- service_role が =app_config= を UPDATE できることは
  =supabase/tests/database/03_grants_test.sql= で固定してある

*** 経緯
当初は =latest_version= との完全一致 (=!== ) で判定していた。これは「床」ではなく
特定の一点にだけ嵌まる「掛け金」で、サーバ側がアプリより古い場合もブロックされた。
本番の行が既定値 =1.0.0= のまま放置されていたため、実際にその状態だった。
=mobile/pubspec.yaml= / =supabase/seed.sql= / 本番の行という3つの写しを
手で一致させ続ける必要もあった。

=0009_app_config_min_required_only.sql= でセマンティック比較に切り替え、
「更新のお知らせ」用の =latest_version= 列は削除した (ストアが既に通知するので不要、
かつ未使用の列を放置したことが今回の脆さの原因そのものだったため)。
これにより3つの写しを同期する必要自体が無くなっている。

  実行するので、設定が ON でも OFF でも最終的な権限は同じになる。
  つまりこの設定に依存しない状態になっている
- ただしダッシュボードで後から ON に戻すと =alter default privileges= が
  再設定され、**それ以降に作ったテーブル**が =anon= / =authenticated= に
  自動公開される。マイグレーションで作るテーブルにも影響する
- テーブルを追加したら =supabase/migrations/= の新しいファイルで
  =grant ... to authenticated= を明示すること。
  付け忘れると =permission denied for table= になるので、気付かないまま
  公開されるより安全側に倒れる
- 権限そのものは =supabase/tests/database/03_grants_test.sql= の
  =table_privs_are= で固定してある
