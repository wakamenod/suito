* Suito
** 全体の構成

** 試したこと (Flutter)
- ローカライズは[[https://pub.dev/packages/slang][slang]]を使用
- [[https://pub.dev/packages/envied][envied]] で環境変数の取得
- firebase_authを使った認証
  - [[https://pub.dev/packages/firebase_auth][firebase_auth]]
  - [[https://pub.dev/packages/firebase_ui_auth][firebase_auth_ui]]
  - IdTokenを送信して自前のバックエンドで認証
- [[https://pub.dev/packages/riverpod][riverpod]]で状態管理
- [[https://pub.dev/packages/go_router][go_router]]での画面遷移・ルーティング
- Flutter webでアカウント削除ページの作成
- [[https://pub.dev/packages/dio][dio]] をつかったAPI通信
  - モデル部分はopenapiによる自動生成
- unitテスト、widgetテストの導入
  - Goldenテスト導入 ([[https://pub.dev/packages/golden_toolkit][golden_toolkit]])
  - [[https://pub.dev/packages/mocktail][mocktail]] を使用しモックを使ったテストの導入
- フォーム実装およびバリデーションは[[https://pub.dev/packages/formz][formz]]を使用
- サーバーバージョンチェック
  - アプリバージョンと不一致の場合ストアへ遷移
- [[https://pub.dev/packages/syncfusion_flutter_charts][syncfusion_flutter_charts]] によるチャートの実装

- Webフレームワークは [[https://github.com/labstack/echo][echo]] を使用

- 簡単な3層レイヤーを導入
- [[https://github.com/swaggo/swag][swag]] を使ったSwaggerドキュメント生成

*** TODO 論理削除したスケジュールから翌月分の取引が1件だけ生成される
=create_transactions_from_queue()= が親スケジュールの =deleted_at= を見ていないため、
論理削除済みのスケジュールでも =scheduled_*_queue= に行が残っていれば、
その1件が取引として materialize されてしまう。

- 発生条件: スケジュール作成 → トリガーが queue に翌月分を積む → ユーザーが削除
  (=deleted_at= を打つだけで queue 行は残る) → 翌月 cron が queue を消化して取引を生成
- 2回目以降は起こらない。=enqueue_transaction_schedules()= は
  =s.deleted_at is null= で絞っているため、消化済みの queue が再度積まれることはない
- Go 版もまったく同じ挙動だった (=CreateExpensesFromScheduledQueue= が raw SQL で
  gorm のソフトデリートを迂回していた) ので、移行で持ち込んだ退行ではない。
  ただしフェーズ4でスケジュール削除が UI から実行できるようになるため顕在化する
- 対応案: =expense_schedule= / =income_schedule= の AFTER UPDATE トリガーで
  =deleted_at= が NULL から非 NULL に変わった行の queue 行を削除する
  (新規マイグレーション =supabase/migrations/0006_*.sql=)。
  =create_transactions_from_queue()= の DELETE ... USING 側に
  =s.deleted_at is null= を足すだけでは、queue 行が永久に残るので不可
- 承認済みのフェーズ2 SQL への変更になるため、フェーズ4では手を入れていない
